`web/` contains the static admin dashboard.

![Dashboard](../assets/img/dashboard-threads.png)

Files:

- `index.html`: dashboard markup.
- `dashboard.js`: dashboard behavior, data loading, filtering, moderation actions, session handling, graph rendering, and UI state.
- `styles.css`: dashboard layout, light/dark theme, responsive behavior, popovers, modals, and thread visuals.

Open `index.html` in a browser or serve it from a static host. The dashboard talks directly to the deployed Worker admin endpoints.

## Recommended Hosting

For production, host the static dashboard on your site, usually under `/urthreads/`:

```text
Dashboard UI: https://www.myblog.com/urthreads/
Worker API:   https://urthreads-worker.your-subdomain.workers.dev
```

Build it into your static output directory:

```bash
urthreads dashboard set ./public urthreads
urthreads dashboard build
```

The hosted path should serve `index.html`, `dashboard.js`, and `styles.css` from `/urthreads/`. `dashboard build` refreshes the saved install after package updates.

When the dashboard opens, enter the Worker API origin, such as:

```text
https://urthreads-worker.your-subdomain.workers.dev
```

The dashboard uses this base URL to call protected admin endpoints such as `/admin/session`, `/admin/summary`, `/admin/comments`, and `/admin/likes`.

Add the dashboard origin to `ALLOWED_ORIGINS`. The origin is only scheme plus host plus optional port; it does not include `/urthreads/`.

```bash
urthreads env add-origin https://www.myblog.com
urthreads wrangler set ALLOWED_ORIGINS https://www.myblog.com
wrangler deploy
```

Serve the dashboard over HTTPS in production. The dashboard refuses to start a cookie session with a plain `http://` worker origin except for the local development hosts `localhost`, `127.0.0.1`, and `[::1]` (any port); any other host entered over `http://` is rejected before the admin key is sent. `web/index.html` also ships a strict Content-Security-Policy and a no-referrer policy; `connect-src` allows `https:` worker origins plus the localhost development origins above.

## First Login

Before using the dashboard, create an admin key and configure the deployed Worker:

```bash
urthreads admin-key
urthreads admin-session --ttl 1h
```

`urthreads admin-key` copies the key to your clipboard and can optionally store it as the deployed Worker secret. Expiring keys can also update `ADMIN_API_KEY_EXPIRES_AT` in `wrangler.toml` and prompt for deployment.

If you skip the automated expiration update, run:

```bash
urthreads wrangler set ADMIN_API_KEY_EXPIRES_AT "2026-06-01T02:26:56.380Z"
wrangler deploy
```

Then open the dashboard and enter:

- Worker URL: `https://your-worker.workers.dev`
- Admin key: the value generated by `urthreads admin-key`

The admin key is submitted once to `POST /admin/session`. The Worker returns an `HttpOnly`, `Secure`, `__Host-` prefixed session cookie scoped to `Path=/`. The dashboard does not store the raw key or a JavaScript-readable session token.

Refresh persistence depends on the cookie being accepted by the browser. For cross-origin dashboard use, add the exact dashboard origin to `ALLOWED_ORIGINS` and redeploy the Worker.

Example local origins:

```bash
urthreads env add-origin http://localhost:8000
urthreads env add-origin http://[::1]:8000
```

## Session Menu

When connected, the session indicator in the header opens a small session menu. Use **Log out** to call `DELETE /admin/session`, expire the cookie, clear dashboard state, and reload.

If the session expires, the dashboard keeps the Worker URL and asks for the admin key again.

## Overview

The Overview section shows:

- total page likes
- total comment likes
- pending comments
- approved comments

The icons use neutral colors by default and reveal their metric colors on hover.

## Engagement Trend

The engagement graph shows activity over:

- `1D`
- `7D`
- `14D`
- `30D`

Use the date picker to choose the start date. The date picker prevents ranges that would end past today's available data, so a selected range always has a full window.

The graph combines:

- page likes from `engagement_events`
- comment likes from `engagement_events`
- comment submissions from `engagement_events`
- moderation actions from `admin_audit_logs`

The legend stays in the section header; range and date controls sit in the collapsible content area.

## Comments

The Comments section supports:

- status filtering: all, pending, approved, hidden, rejected
- path search
- result limit
- denied keyword popover
- auto-approve toggle
- threaded display
- approve, reject, hide, unhide, restore, and delete actions

Comment status behavior:

- `pending`: waiting for moderation.
- `approved`: visible publicly unless hidden.
- `hidden`: approved but not shown publicly.
- `inactive`: shown in the dashboard when a parent is hidden; child controls are disabled while inactive.
- `rejected`: rejected by moderation or denied keyword matching.

Rejected comments include special restore logic. Restoring a rejected comment prompts a warning because it may include a denied keyword. Permanently deleting a rejected comment uses a trash action.

Deleting a comment that has replies warns the user that child replies will also be deleted. The Worker deletes descendants recursively.

## Denied Keywords

![Denied Keywords](../assets/img/denied-keywords.png)

The denied keywords popover lets moderators add and remove automatic rejection keywords.

Behavior:

- Add a keyword directly from the popover.
- Existing keyword badges are neutral by default.
- Hovering a badge turns it red.
- First click arms the badge for deletion and replaces text with a trash icon.
- Second click deletes the keyword.
- Clicking elsewhere, closing the popup, or waiting five seconds cancels the armed state.

The popover should not close when interacting inside it.

## Posts

The Posts section ranks paths by:

- relevance
- likes
- comment likes
- comments
- recent activity

The path title display shows only the page title where available. Hovering the title opens a small popup with the path and "Click to copy path"; clicking copies the path only.

## Activity Logs

The Activity Logs section shows protected dashboard activity from `admin_audit_logs`.

Filters:

- selected date
- request type
- path search
- result limit

Logs include action, method, route, status, timestamp, client metadata, and sanitized details. The client IP comes from Cloudflare's `CF-Connecting-IP` header; `X-Forwarded-For` is never trusted. Raw admin keys and request bodies are not stored.

## Cloudflare Worker

The Cloudflare Worker section displays runtime information returned by `/admin/worker`, plus a link route to the Cloudflare dashboard. It is informational and does not expose Cloudflare account API tokens.

## Responsive Layout

The dashboard is responsive:

- The site header and session info stay opposite each other on mobile and desktop.
- Comments, posts, and activity logs remain vertical sections.
- Filter bars collapse into mobile-friendly rows when needed.
- Path search and limit controls share a row on mobile where appropriate.
- Thread arms are rendered for nested comments and account for deeper reply levels.

## Local Development

For static testing, serve the repository root or `web/` directory and open `web/index.html`.

Examples:

```bash
python3 -m http.server 8000
```

Then open one of:

- `http://localhost:8000/web/index.html`
- `http://[::1]:8000/web/index.html`

Whichever browser origin you use must be present in `ALLOWED_ORIGINS` for cookie sessions to work. The dashboard's https gate permits plain `http://` only for `localhost`, `127.0.0.1`, and `[::1]` worker origins, so the local commands above keep working.

### Local testing (no Cloudflare account needed)

To run the Worker and dashboard locally without Cloudflare credentials:

```bash
npm install
npm run setup:dev    # writes .dev.vars (admin key, never-expiring), initializes local D1
npm run dev          # wrangler dev on http://localhost:8787
```

In a second terminal serve the dashboard:

```bash
python3 -m http.server 8000
```

Open `http://localhost:8000/web/index.html`, set **Worker URL** to `http://localhost:8787`, and paste the admin key that `npm run setup:dev` printed. `ALLOWED_ORIGINS` includes `http://localhost:8000` by default (see `wrangler.toml`), so the cookie session works over plain HTTP.

`setup:dev` always writes `ADMIN_API_KEY_EXPIRES_AT=` (never-expiring) into the gitignored `.dev.vars`, so a stale or expired local key can never lock you out — re-run `npm run setup:dev` to reset it, then restart `npm run dev`. Local sessions use the un-prefixed `urthreads_admin_session` cookie (no `__Host-`/`Secure`) because browsers drop `Secure` cookies over HTTP; deployed HTTPS sessions keep the `__Host-urthreads_admin_session` cookie with `Secure`.

After changing dashboard assets, bump the query strings in `index.html` so browsers fetch the latest files:

```html
<link rel="stylesheet" href="styles.css?v=..." />
<script src="dashboard.js?v=..."></script>
```

Security releases bump these versions; the guidance above covers future bumps.
